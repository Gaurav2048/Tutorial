Before you start

What is an agent harness?

An agent is a language model that can decide to take actions, see what happened, and decide again. The harness is everything around the model that makes that possible and safe: the loop, the tools, the permissions, the context, the persistence. The model supplies judgment; the harness supplies hands, eyes, memory and guardrails.

Prerequisites: Node 20+, an Anthropic API key, comfort with TypeScript and async/await. Every code sample builds on the previous one, so follow in order. Models change quickly, so the model name is kept in one constant you can swap, and the API shapes shown (messages, tool_use, tool_result) are the stable core.

Level 1

Foundations: the loop

Goal: a model that can call one fake tool in a loop.

STEP 1 Setup and your first call

Goal: project skeleton, one successful request to the model.

Run it with npx tsx src/hello.ts. Notice two things: content is an array of blocks (not a string), and there is a stop_reason. Both matter for everything that follows.

Also remember that the API is stateless. The model remembers nothing between calls. Whatever it needs to know, you send again each time. A big part of a harness's job is deciding what to send.

STEP 2 Anatomy of tool use

Goal: understand the exact message protocol the loop depends on.

A tool is described to the model with a name, a description and a JSON Schema. The model never runs anything. It only asks you to, by returning a tool_use block. You run it and reply with a tool_result block whose tool_use_id matches.

Rules that cause 90% of early bugs
  • Every tool_use must be answered by a tool_result with the same id, in the very next user message.
  • If the model made several tool calls in one turn, return all results together in one user message.
  • Always push the assistant's content back unchanged, not just its text.

STEP 3 The agent loop

Goal: the ~25 lines that are the heart of every agent.

Call the model. If it asks for tools, run them, append the results, repeat. If it doesn't, you're done. That's the entire idea.

Try itAdd a second tool, add(a, b), and ask a question that needs both. Watch the model chain calls across turns.

This is already a real agent. Everything below makes it useful (better tools), safe (control), pleasant (UX), and durable (long tasks).

Level 2

Real tools

Goal: a tool registry with file and shell tools that fail gracefully.

STEP 4 A tool registry

Goal: keep each tool's schema and implementation together; make adding tools trivial.
Key ideaNever let a tool exception crash the loop. Catch it and return it as an is_error result. Models are good at reading an error and trying something else; that's how they self-correct.

STEP 5 File and shell tools

Goal: the minimum toolset for a coding-style agent: read, write, list, run.
This is not a sandboxexec with a working directory does not stop rm -rf ~. Real isolation comes from running the whole harness in a container or VM with limited mounts and network (Step 8). The approval prompt is a second layer, not the only one.

STEP 6 Tool design models use well

Goal: learn the design rules that matter more than any code.

Tool quality is the biggest lever on agent quality. The model only knows your tool by its name, description and schema, so treat those as a prompt.

RuleWhy
Describe when to use it, not just what it does"Search the codebase for a string. Use before reading files you haven't located."
Return errors that teach"File not found: src/a.ts. Did you mean src/app.ts?" lets the model recover in one step.
Cap output size, and say it was cappedA 2 MB log in context wastes money and buries signal. Tell the model how to get more (offset, filter).
Fewer, sharper toolsTen overlapping tools confuse selection. Merge near-duplicates.
Make dangerous things explicitSeparate read_file from write_file. Don't hide writes inside a generic "do" tool.
Prefer human-readable outputPaths and names beat opaque IDs. Include just enough to act on.
Try itAdd a search tool (ripgrep or a JS grep) that returns file:line: text capped at 100 matches, with a trailing "N more matches, narrow your pattern" message.

Level 3

Control and safety

Goal: an agent you would trust to run unattended.

STEP 7 The system prompt

Goal: give the model its role, environment, and working style.

Good system prompts are short, concrete, and describe behaviour you can observe ("run the tests before saying done") rather than adjectives ("be thorough"). Put anything that changes per run (date, cwd, git status, project notes) in here so the model doesn't have to discover it.

Project memory fileMany harnesses auto-load a NOTES.md / AGENTS.md from the workspace into the system prompt. It's the cheapest way to give the agent project conventions: build commands, style rules, gotchas.

STEP 8 Permissions and sandboxing

Goal: defence in depth: policy, approval, and isolation.

Think in three layers, from cheapest to strongest:

  • Policy: rules that auto-allow, auto-deny, or ask. Pure code, instant.
  • Approval: a human confirms risky actions.
  • Isolation: a container/VM so even an approved or mistaken action can't hurt you.

Then call policy() inside the registry's execute before running a tool. On "deny", return an is_error result explaining why, so the model can adapt instead of retrying forever.

Prompt injectionAnything the agent reads (web pages, issues, files, tool output) can contain instructions aimed at it. Treat tool output as data, never as commands. The defence isn't a clever prompt; it's limiting what the agent can do (least-privilege tools, no secrets in reach, approval on anything with side effects or network egress).

STEP 9 Limits, budgets, cancellation

Goal: an agent that can't loop forever or burn your wallet.

Upgrade the loop from Step 3 into the production shape. It now uses the registry, enforces turn/token budgets, handles every stop reason, and supports cancellation.

Why "continue" instead of failing?Hitting max_tokens mid tool-call produces a malformed call. Handling it explicitly is a classic harness detail that separates demos from tools people rely on.

Level 4

Experience and durability

Goal: it feels alive, and survives restarts.

STEP 10 Streaming

Goal: show text as it's generated and surface tool activity live.

Waiting 20 seconds for a wall of text feels broken. Streaming fixes perceived latency and lets users interrupt early. The SDK's stream helper gives you events plus the assembled final message, so the rest of your loop barely changes.

Treat these callbacks as your event bus. Later, a web UI, a log file, and your eval runner can all subscribe to the same events without touching the loop.

STEP 11 Sessions and persistence

Goal: crash-safe transcripts and the ability to resume.

Since the API is stateless, your transcript is the agent's memory. Append every message to a JSONL file as it happens. If the process dies, you lose nothing.

Wire it in by calling session.append() wherever the loop does messages.push(). To resume, pass session.messages in as o.messages and send the next user message.

Resume correctnessA transcript that ends on an assistant tool_use with no matching tool_result is invalid. On resume, detect that and either re-run the tool or append an is_error result saying "interrupted". Also store a version number with sessions so you can migrate formats later.

Level 5

Advanced harness engineering

Goal: long-running, extensible, measurable agents.

STEP 12 Context management

Goal: keep long tasks inside the context window without losing the plot.

Every turn re-sends the whole transcript. Tool outputs dominate it. Left alone, a long task will blow the window or get slow and expensive. Three techniques, from cheap to heavy:

1. Prompt caching: mark the stable prefix (system prompt, tool schemas) so repeated turns are cheaper and faster.

2. Clear stale tool results: old file dumps and command output are rarely needed verbatim again.

3. Compaction: when usage nears the limit, have the model summarise the older transcript and continue from the summary.

Rule of thumbCheap tricks first (cache, clear, truncate at the tool). Compaction is lossy; use it as the last resort and write summaries that preserve exact identifiers.

STEP 13 Planning with a todo tool

Goal: help the model stay on track across dozens of steps.

A surprisingly effective trick: give the model a tool whose only job is to write its own plan down. It does nothing on the machine, but it keeps the plan visible in recent context, and gives you a progress UI for free.

Render the list in your UI on every call. Users can see what the agent intends to do before it does it, which is also a good moment to let them correct it.

STEP 14 Subagents

Goal: delegate big, noisy sub-tasks to a fresh context.

A subagent is just your own runAgent called from inside a tool. It gets a clean context, a narrower toolset, and returns only a short report. The parent never sees the 40 files it read, which keeps the parent's context small and focused.

When subagents winBig exploratory reads, independent parallel investigations, and isolating risky tools. When they lose: small tasks (the overhead dominates) and tasks needing the parent's full context (the subagent can't see it).

STEP 15 Parallel tool calls and hooks

Goal: speed up the loop and make behaviour programmable without editing it.

Parallel execution. Models often request several tool calls in one turn. Read-only calls are safe to run concurrently; side-effecting ones should run in order.

Hooks. Let callers inject code at defined points: before a tool (veto/modify), after a tool (log/format), at stop (run tests, block "done" if they fail).

In the loop: call hooks.preTool before executing (a deny becomes an is_error result), postTool after, and onStop when the model says it's done. If onStop returns continueWith, push that as a new user message and keep looping. This "don't stop until the check passes" pattern is one of the most valuable things a harness can add.

STEP 16 Extensibility: skills and MCP

Goal: add capabilities without bloating the prompt or the codebase.

Skills (progressive disclosure). Instead of stuffing every instruction into the system prompt, keep a folder per skill with a SKILL.md. Put only each skill's name and one-line description in the system prompt, and give the model a load_skill tool that returns the full text on demand.

MCP (Model Context Protocol). An open standard for exposing tools and data to agents over a common interface. An MCP client in your harness connects to servers, lists their tools, and registers each as a Tool in your registry whose run() forwards the call. Your loop doesn't change at all, which is the payoff of the registry from Step 4. Use the official MCP SDK rather than hand-rolling the protocol; check its docs for current APIs.

Trust boundariesThird-party tools are third-party code and third-party prompt text. Namespace their tools (server__tool), apply your permission policy to them, and don't auto-approve tools you didn't write.

STEP 17 Evals and observability

Goal: know whether a change made the agent better or worse.

Agents are non-deterministic and a "small" prompt tweak can silently break other behaviour. Without evals you're guessing. Start tiny: 10–20 realistic tasks, each with an automatic check.

Observability. Log every model request/response and every tool call with a run ID, latency, token usage, and cost. When something goes wrong in production, the transcript plus these traces is how you debug it. Track over time: pass rate, average turns, tokens per task, tool error rate, and how often budgets or limits trigger.

Eval habits that pay off
  • Every real failure you see becomes a new test case.
  • Check outcomes (tests pass, file exists), not exact wording.
  • Change one thing at a time (prompt, tool description, model) and compare pass rates.

Goal: know what's left between "works on my laptop" and "ships".

Where to go next

  • Use a ready-made harness. Anthropic's Claude Agent SDK packages much of this (loop, file/shell tools, permissions, sessions, subagents, hooks, MCP). Building your own first, as you just did, is the best way to understand what it's doing. Check the current docs at docs.claude.com.
  • Read other harnesses' source. Open-source coding agents are great case studies in tool design and context handling.
  • Specialise. A research agent wants web tools and citation checks; a support agent wants ticket APIs and strict permissions; a data agent wants a sandboxed code interpreter.
  • Go multi-agent carefully. Start with the single loop plus subagents-as-tools. Add orchestration only when evals show you need it.
Capstone projectBuild a "fix my failing tests" CLI: it takes a repo path, explores, edits, runs the tests, and refuses to stop until they pass (Step 15 hook). Add an eval with 10 broken fixtures and track your pass rate as you improve prompts and tools.
You now have the mental model: a loop, a registry of well-designed tools, layered safety, durable context, and evals to keep you honest. Everything else is refinement of those five ideas.
