Build QueueLens: your first installable AI developer tool

A practical tutorial for a React, Node.js, and TypeScript developer.

You will build the same category of product as REA: ordinary software exposed as tools that an AI agent can call, plus instructions that teach the agent how to use those tools. This example is deliberately small enough to understand end to end.

Allow approximately 60–90 minutes to study the implementation and complete the exercises. You can run the finished demo in about ten minutes. The source accompanies this tutorial; snippets below explain specific parts rather than replacing the complete files.

1. Choose a problem with observable evidence

Your application sends invoices and emails through background jobs. A support ticket arrives: “Invoice generation is stuck.” Possible explanations include a downstream timeout, a worker losing its processing lock, or a legitimately slow job. Reading many raw records by hand is tedious, and giving an AI a generic “debug my queue” prompt does not provide those records.

Problem statement: Given a normalized snapshot of selected jobs and worker observations, identify suspicious jobs, explain the recorded evidence, and recommend the next investigation steps.

Success criteria:

  • Find the failed invoice that exhausted its execution attempts.
  • Find a different invoice with recorded stalls and failed lock renewal.
  • Flag a long-running active job without claiming that it definitely stalled.
  • Return bounded results and disclose what the snapshot cannot establish.
  • Let a developer use the same capabilities from a terminal or Claude Code.

The finished product is QueueLens. Its first version uses synthetic snapshots so anyone can reproduce the scenario without Redis credentials, a running worker, or paid model access. The final chapter describes the additional work needed to connect real infrastructure.

A BullMQ nuance shapes the whole design: stalled is an event, not a job state. A job can be retried or moved to the failed set after a stall. The stall limit and ordinary execution-attempt limit are separate mechanisms. See the BullMQ stalled-jobs guide.

2. Understand the pieces you are building

Piece Responsibility QueueLens file
Data boundary Validate the snapshot and its records src/schema.ts, src/store.ts
Domain logic Produce findings from observations src/diagnosis.ts
MCP server Describe tools and accept calls from an agent src/server.ts
CLI Launch the server or call the same logic directly src/cli.ts
Skill Explain the investigation workflow to Claude skills/queue-diagnosis/SKILL.md
Plugin packaging Bundle the server and skill for local loading .claude-plugin/plugin.json, .mcp.json

Claude supplies the reasoning and conversation. Your server supplies data and deterministic operations. The skill supplies a reusable procedure. The plugin packages those parts.

When you ask about invoices, Claude discovers the available tool definitions, selects a tool and arguments, receives the results, and may make another call before writing its answer. QueueLens does not embed a Claude API request in its own server. The MCP client—in this case Claude Code—owns the model interaction.

3. Run the finished example first

Unzip the project and open a terminal in the queuelens folder:

node --version
npm ci
npm test
npm run demo

Use Node 22.19 or newer; the project was tested on Node 24.19. Dependencies are pinned, and the lockfile makes installation reproducible.

The demo inspects invoice-103. You should see two finding codes:

["stall_recorded", "lock_renewal_failure"]

It should not include retries_exhausted: that fixture has one recorded execution attempt against a limit of three. Its failure instead reports a stall-limit problem.

Next, compare the other jobs:

node dist/cli.js summary --queue invoices
node dist/cli.js inspect invoice-102 --queue invoices
node dist/cli.js inspect invoice-104 --queue invoices

Expected observations:

Job Finding codes What you can conclude
invoice-102 retries_exhausted, timeout_reported Its recorded timeout persisted through the configured attempts
invoice-103 stall_recorded, lock_renewal_failure Stalls and a failed lock-renewal observation were recorded
invoice-104 long_running Its active duration exceeds the five-minute default threshold

You cannot conclude that Redis disconnected or CPU usage was high: the sample has no measurements proving either explanation. The tool suggests checking those possibilities.

4. Create the TypeScript project

If you are rebuilding this from scratch, begin with an npm project and install the MCP server SDK, Zod and TypeScript. QueueLens uses the SDK's 2.x package layout:

mkdir queuelens
cd queuelens
npm init -y
npm install @modelcontextprotocol/server@2.3.1 zod@4.4.3
npm install -D typescript@5.9.3 @types/node@24.10.0

Set "type": "module" in package.json. The supplied tsconfig.json uses NodeNext for both module settings, src as the source root, and dist as the compiled destination. Relative TypeScript imports use .js so the emitted JavaScript works with Node's ESM resolver.

The official MCP server tutorial documents the SDK. Older examples may use @modelcontextprotocol/sdk/server/mcp.js; this project consistently uses the newer split package, @modelcontextprotocol/server. Do not mix import paths from different SDK generations.

Build with npm run build. Inspect the short files before expanding the project: the goal is to understand the boundaries, not to begin with a large framework.

5. Design the data contract before the tools

Open fixtures/demo.json. It contains a capture time, a reporting-window label, a scope description, and selected records for two queues.

Each job has:

  • Identity: queue name, job ID, job name.
  • Current observed state: waiting, active, completed, failed or delayed.
  • Timing: creation, processing and finishing timestamps when available.
  • Attempts and an optional recorded failure message.
  • Selected events with their observation timestamps.

QueueLens uses the pair (queue, id) as identity. Two queues may legitimately contain the same job ID.

This is QueueLens's normalized format, not a raw BullMQ export. An adapter must deliberately map its source data into this contract. In particular, lock_renewal_failed is a normalized worker observation, not a promise that BullMQ exposes an identically named global queue event.

Open src/schema.ts. Zod validates input before analysis. The schema rejects unknown fields, excessive record counts, duplicate identities, impossible timestamp ordering and observations after the capture time. store.ts also rejects input files larger than 5 MiB.

The server reloads the configured file for every call. That keeps the adapter simple and allows a snapshot to be replaced between calls. It also means an investigation can span more than one capture; the returned capture timestamp lets the agent notice that change.

For a coherent production investigation, introduce an immutable snapshot ID or retain a snapshot across the investigation. That is an extension, not behavior implemented here.

6. Implement plain functions first

Read src/diagnosis.ts before the MCP wrapper. You will find three ordinary functions:

summarize(snapshot, queue)
listProblems(snapshot, queue, limit, longRunningMs)
inspectJob(snapshot, queue, jobId, longRunningMs)

They do not need a model, an HTTP server, or Claude. This makes the core useful and testable on its own.

Consider the long-running check:

const age = Date.parse(snapshot.capturedAt)
  - Date.parse(job.processedAt);

if (age > longRunningMs) {
  // Return an observation and suggested next checks.
}

Notice that it uses the snapshot's capture time instead of Date.now(). Running the same historical fixture tomorrow should not change a twelve-minute job into a day-long job.

A finding contains a stable code, an observation, evidence and next checks. For example, timeout_reported points to the recorded failure message. It does not claim that the downstream service was definitely overloaded. This distinction makes the result more useful than a confident but unsupported diagnosis.

listProblems returns matchingJobs, a bounded list and a truncated flag. Without these fields, an agent could mistake the first ten records for the entire result set.

The example includes a small common-pattern redactor for token and email strings. It is not a complete secret-detection system. Before connecting actual logs, define a field allowlist and sanitize data at ingestion. Error strings can contain information beyond these patterns.

7. Turn functions into MCP tools

Read src/server.ts. The server's tool catalog is a public interface, much like a REST API. A tool needs a useful name, a description, an input schema and a handler.

This excerpt is from the actual implementation:

server.registerTool('get_queue_summary', {
  description: 'Count job states and recorded stalls in a configured snapshot. Counts are observations, not guaranteed live queue totals.',
  inputSchema: z.object({ queue: queueName.optional() }),
  annotations,
}, ({ queue }) => run(s => summarize(s, queue)));

The name helps the agent identify the operation. The description explains when to use it and what its output means. The schema defines valid arguments. The handler calls your existing function.

run() loads a validated snapshot and wraps the output. Successful calls provide both JSON text and structuredContent. Error calls return isError: true. A missing job is distinguished from unusable input data without exposing raw validation details or file contents.

The three tools are:

Tool Arguments Why it exists
get_queue_summary Optional queue Discover queues and obtain observed counts
list_problem_jobs Optional queue, bounded limit, duration threshold Narrow a large snapshot to relevant records
inspect_job Queue, job ID, duration threshold Get evidence and next checks for one record

The snapshot path is configuration for the server process. It is not an arbitrary path supplied by the model in each tool call. Tool input schemas are part of your product design: expose the operation the user needs.

Annotations mark the tools as read-only. These annotations are hints to clients, not permission enforcement. The implementation is read-only because its handlers only load and inspect the snapshot.

8. Launch the server through stdio

In src/cli.ts, the serve command starts the protocol process:

serveStdio(() => createServer(snapshotPath), {
  onerror: error => console.error('QueueLens protocol error:', error.message),
});

The factory returns a fresh server instance as required by the SDK's protocol negotiation. The supplied integration tests exercise both modern and legacy clients.

For a stdio server, stdout carries protocol messages. Sending a friendly console.log('Server ready') there can corrupt communication. Send operational logs to stderr using console.error instead. The CLI's non-server commands are different: they intentionally print JSON to stdout.

Running npm start in a terminal starts a process waiting for an MCP client. Silence is expected. It is not a web server, and there is no browser page or TCP port for this transport.

9. Verify the real MCP boundary

Run:

npm test

The project has eight tests. tests/diagnosis.test.mjs verifies the domain rules, redaction, bounded output, snapshot validation and CLI behavior. tests/mcp.test.mjs spawns the compiled server, connects an SDK client over stdio, discovers the tools and calls all three of them.

The protocol test also sends invalid arguments, checks missing-job errors and confirms that the fixture bytes did not change. It runs once with a legacy handshake and once with a modern pinned protocol revision.

This matters because a passing function test does not prove your executable starts, its import paths resolve, or the tool contract works across the process boundary.

The automated test client is a useful development tool. It exercises your server without paying for a model request or relying on an agent to select the right tool. Testing model behavior itself requires a separate set of agent evaluations.

10. Add the skill that teaches the investigation

Open skills/queue-diagnosis/SKILL.md.

The frontmatter names the skill and explains its purpose. disable-model-invocation: true makes this tutorial's workflow explicitly invoked by the user. $ARGUMENTS receives the queue or job description after the command.

The workflow starts with a summary, narrows to problem jobs and then inspects individual records. It requires evidence, capture times and uncertainty in the final answer. It also prevents the agent from treating error messages as instructions or claiming to have inspected live Redis.

A skill changes the procedure the model follows. The MCP server supplies the operations and data that make that procedure possible. You can change the skill's reporting format without changing the server, or reuse the server in another MCP client with different instructions.

For project installation, the skill goes in .claude/skills/queue-diagnosis/SKILL.md. For plugin loading, it stays in the plugin's skills/ directory and receives a plugin-qualified command. See Claude Code skills.

11. Connect it to Claude Code

Choose one of the following development paths.

Path A: load the local plugin

Build first, then start Claude Code with an absolute path:

npm ci
npm run build
claude --plugin-dir /absolute/path/to/queuelens

This loads the plugin manifest, skill and MCP configuration. Inside the session:

/mcp
/queuelens:queue-diagnosis invoices

The .mcp.json file uses ${CLAUDE_PLUGIN_ROOT} to locate the compiled executable. The standard plugin layout and path variables are documented in the plugin manifest reference.

Path B: install into an existing project

From the QueueLens folder, preview setup:

npm run setup:claude -- --project /absolute/path/to/your-app

The command prints the registration arguments and destination skill directory. It does not apply changes without --apply:

npm run setup:claude -- --project /absolute/path/to/your-app --apply

The setup command runs the installed Claude CLI in the target project and copies the skill. It refuses to overwrite an existing skill. It uses argument arrays rather than building a shell command string, so paths with spaces remain single arguments.

Restart Claude Code in your target project, inspect /mcp, and invoke:

/queue-diagnosis invoices

The command is unqualified here because this is a project skill rather than a plugin skill. Choose one path to avoid loading duplicate tools and skills.

For manual MCP registration, the equivalent shape is:

claude mcp add --transport stdio --scope local queuelens \
  -- node /absolute/path/to/queuelens/dist/cli.js serve

You would separately copy the skill into the target project's .claude/skills/ directory. The setup command automates those two steps. Claude Code's documentation explains MCP registration and scopes.

Verification prompt: “Use QueueLens to investigate the invoices queue. Show observed evidence separately from possible causes.”

An appropriate response identifies the two failed jobs and the long-running active job, names the capture time, and discloses that the input is synthetic. Its exact prose will vary. You should see actual tool calls; a convincing answer alone is not proof that the integration ran.

12. Trace one complete investigation

The prompt names the invoices queue. The skill guides Claude to call get_queue_summary with queue: "invoices".

The summary reports five observed jobs: one waiting, one active, one completed and two failed. These are snapshot counts, not a complete live-queue claim.

Claude then calls list_problem_jobs. It receives three matches for invoices: invoice-102, invoice-103 and invoice-104.

It can inspect each result. For invoice-103, the evidence includes failed lock renewal at 17:43:31Z and stalled events at 17:44:01Z and 17:45:01Z. Those timestamps suggest when to examine worker and Redis observations, but they do not prove the cause.

This is the reusable product pattern: gather reliable evidence through software, organize the investigation through instructions, and let the model synthesize the findings.

13. Make it installable for other developers

The included CLI has a shebang, a bin entry in package.json, and a setup command. These are the building blocks behind commands such as npx some-package setup.

Before publishing your own version:

  1. Choose an available npm package name and update the manifest.
  2. Remove "private": true only when you intend to publish.
  3. Add a license and clear support information.
  4. Add a prepack build step so the executable exists in the tarball.
  5. Run tests, inspect npm pack --dry-run, and test a packed installation in a clean directory.
  6. Publish to npm and put the source in a GitHub repository.

This tutorial has not published anything. The package name is an example, not a claim that it is available.

After you publish an executable package, a user's installation command could look like:

npx YOUR_PUBLISHED_PACKAGE setup --project /path/to/app --apply

Keep setup deliberate and visible. Avoid an automatic postinstall script that edits agent configuration unexpectedly.

For Claude's marketplace distribution, add a marketplace catalog or publish through an existing one. A plugin manifest describes the plugin; a marketplace catalog lists where plugins are obtained. Build and dependency availability must be handled before declaring a marketplace release usable. The included configuration demonstrates local loading after npm ci and npm run build.

14. Extend it to real BullMQ data

The current product analyzes normalized snapshots. Connecting Redis is a separate adapter project, and it requires more than replacing a JSON read with one API call.

A collector would gather selected jobs and their current states from a Queue, retain lifecycle observations from QueueEvents, and correlate worker logs. BullMQ's job getters and events guide are useful starting points.

Define the queue allowlist, the retention window and the maximum number of records. Preserve which observations came from the queue, the worker or your own monitoring. Do not fabricate event history from current job state.

The QueueLens adapter boundary is loadSnapshot(). One option is to build a collector that writes this exact JSON schema atomically. Then your MCP server and skill can remain unchanged. Another is to introduce a store interface backed by a monitoring API, returning the same normalized contract.

For atomic file replacement, write the complete new snapshot to a temporary file and rename it into place. This avoids a tool reading half-written JSON. The current loader returns an error for malformed input rather than continuing with partial data.

A useful second release would add queue pause/rate-limit observations, downstream timings and event-loop-delay measurements. These observations allow better explanations. Retrying jobs or changing workers would require separately designed mutation tools, explicit user intent and idempotency handling; the current tools perform no such operations.

15. Practice by adding one useful capability

Exercise A: make the duration threshold visible. Invoke inspect_job for invoice-104 with longRunningMs: 900000. Its twelve-minute duration no longer exceeds the threshold. Explain why a threshold is not itself a diagnosis.

Exercise B: add get_failure_groups. Group failed records by a stable classification such as timeout or authentication failure. Return counts, representative job identities and scope metadata. Avoid grouping by the entire raw message, which can contain unique IDs or sensitive strings. Test the plain function and a real MCP call.

Exercise C: test an overlapping job ID. Add an invoice-103 record to the emails queue. Confirm that inspect_job uses the requested queue and does not accidentally inspect the invoice record.

Exercise D: change the report, not the tools. Modify the skill to produce an incident note with observed facts, candidate causes and missing measurements. Observe which changes belong in the skill versus the server.

Exercise E: collect agent evaluations. Prepare several representative prompts, including a healthy queue, a timeout, a stall-limit failure and an ambiguous long-running job. Record whether Claude selects the right tools and keeps uncertainty in its answer. Automated protocol tests establish connectivity; these evaluations assess the whole workflow.

16. Troubleshoot the common failures

Symptom Likely check
MCP process fails immediately Build first; check Node version and the configured absolute path
Tool registration exists but tools are unavailable Inspect /mcp and the process error; registration is not the same as a connected server
Protocol errors appear after a startup message Remove server console.log calls; stdout belongs to MCP
Skill command is missing Check project versus plugin installation and the corresponding command name
Setup refuses to overwrite the skill Review the existing skill before updating it; manual replacement is deliberate
A live job is not found The configured snapshot may be synthetic, sampled or old
The model confidently claims a Redis outage Require measured evidence and correct the skill/evaluation; a stall alone does not prove that claim

What was tested and what you should verify locally

The shipped project compiles and passes eight automated tests, including real MCP subprocess calls with two protocol handshakes. No model API key is needed for those checks.

The actual Claude Code UI, claude mcp add execution, plugin loading and Redis integration were not exercised in the build environment. Verify the Claude integration with /mcp and visible tool calls on your computer. Redis integration is an extension chapter, not a shipped feature.

Your first milestone is to run the demo, inspect the domain logic, connect Claude, and complete Exercise B. That gives you practical experience with the pieces behind an installable repository: implementation, tool contracts, workflow instructions, testing, setup and distribution.

Companion source, tests, fixture and skill are included in the same project. This tutorial works offline; documentation links require internet access.
